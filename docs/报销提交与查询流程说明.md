# 报销提交与按提交人查询流程说明

本文以当前源码为准，说明一张报销单从公开输入、金额处理、保存到按提交人查询返回的完整路径。不介绍任何未实现的功能；文中每个结论都标注了对应的文件位置，可按输入顺序逐条核对。

- 产品代码：`expense_desk/cli.py`（全部逻辑所在）、`expense_desk/__main__.py`（入口转发）
- 公开使用方式：`README.md`
- 行为佐证：`test_expense_regression.py`（通过子进程调用公开命令的回归测试）

## 1. 公开入口

README.md 第 7 行公开的唯一入口是命令行：

```sh
python -m expense_desk --db <SQLite 文件> <submit|list> ...
```

`expense_desk/__main__.py:1-4` 把该入口转发到 `expense_desk/cli.py` 的 `main()`。`--db` 为必填参数（`cli.py:82-86`），指定 SQLite 数据库文件；相对路径按当前工作目录解释（`cli.py:100-102` 注释），父目录存在时由 `sqlite3.connect` 自动创建新库。

两个子命令在 `build_parser()`（`cli.py:77-97`）中定义：

- `submit --submitter <提交人> --purpose <用途> --amount <金额>`：三个参数均必填（`cli.py:89-92`）。
- `list --submitter <提交人>`：参数必填（`cli.py:94-95`）。

除上述命令行入口外，当前没有 HTTP、图形界面或其他公开入口。`expense_desk/__init__.py` 仅导出 `cli` 模块名，不构成额外的公开编程接口承诺。

## 2. 提交人、用途、金额如何进入系统

`main()`（`cli.py:145-178`）先用 argparse 解析命令行，再按子命令分支：

- submit 分支（`cli.py:150-164`）：依次取 `args.submitter`、`args.purpose`、`args.amount` 三个字符串。
- list 分支（`cli.py:165-169`）：取 `args.submitter`。

三个值都以原始字符串形式进入校验环节，argparse 本身不做任何内容转换。

## 3. 保存之前发生的检查

submit 分支在触碰数据库**之前**完成全部校验（`cli.py:151` 注释明确此顺序）：

1. 提交人：`_clean_name("提交人(submitter)", ...)`（`cli.py:152` → `cli.py:70-74`）。去除首尾空白（`str.strip()`），结果为空则抛出 `ValidationError`；否则以清理后的值继续。
2. 用途：同一函数 `_clean_name("用途(purpose)", ...)`（`cli.py:153`），规则相同。
3. 金额：`parse_amount()`（`cli.py:154` → `cli.py:41-67`），详见第 4 节。

三项全部通过后，才调用 `_insert_expense()` 打开数据库并写入（`cli.py:155-157`）。因此任何校验失败都发生在建库/写库之前。

list 分支只对提交人做同样的 `_clean_name` 清理（`cli.py:166`），随后查询。

## 4. 金额处理：外部输入、保存值、返回值

金额在三个阶段的表示不同，规则全部在 `parse_amount()`（`cli.py:41-67`）：

**外部输入**：一个字符串，如 `"12.30"`。先 `strip()` 去首尾空白（`cli.py:49`），空串直接拒绝（`cli.py:50-51`）。随后用正则 `\A([0-9]+)(?:\.([0-9]{1,2}))?\Z`（`re.ASCII`）做全串匹配（`cli.py:24`、`cli.py:52-56`）：只接受 ASCII 数字整数，或整数部分加小数点及一至两位小数。该正则显式排除全角数字、科学计数法、正负号、千分位等写法（`cli.py:22-23` 注释）。

**保存值**：换算为整数分。做法是字符串拼接——整数部分拼上补足两位的小数部分（无小数时拼 `"00"`），再整体转 `int`（`cli.py:58-59`）。例如 `"12"` → `1200`，`"12.3"` → `1230`，`"12.30"` → `1230`，`"0.01"` → `1`。全程不经过浮点运算，因此**不存在四舍五入或截断环节**：格式不符合"至多两位小数"的输入（如 `12.300`）在正则阶段即被拒绝，而不是被舍入。换算后再做两项数值检查：必须大于零（`cli.py:60-61`），且不超过 SQLite 64 位有符号整数上限 `2**63 - 1` 分（`cli.py:17-18`、`cli.py:62-66`）。

**返回值**：保存成功后，标准输出打印一条 JSON 对象（`cli.py:158-164`、`cli.py:177`），其中 `amount_minor` 字段就是上述整数分值，与入库值完全相同；查询返回的 `amount_minor` 直接取自数据库列（`cli.py:133-141`），不再做任何换算。即：外部输入是元为单位的字符串，系统内部保存值与所有返回值均为整数分，二者只在 `parse_amount()` 一处发生转换。

## 5. 一条报销记录实际包含的业务信息

表结构在 `_SCHEMA`（`cli.py:26-34`），一次 submit 对应 `expenses` 表的一行（`cli.py:112-116` 的单条 `INSERT`）：

| 列 | 类型 | 内容来源 |
|---|---|---|
| `id` | INTEGER PRIMARY KEY AUTOINCREMENT | SQLite 分配的稳定正整数，提交返回值取自 `cursor.lastrowid`（`cli.py:117`） |
| `submitter` | TEXT NOT NULL | 去首尾空白后的提交人 |
| `purpose` | TEXT NOT NULL | 去首尾空白后的用途 |
| `amount_minor` | INTEGER NOT NULL，CHECK > 0 | 整数分金额 |
| `status` | TEXT NOT NULL | 固定写入 `"pending"`（`cli.py:20`、`cli.py:115`） |

记录不含提交时间、币种（README 规则区说明币种固定为人民币，不落库）等字段。相同内容重复提交会生成 id 不同的独立记录（自增主键决定，回归测试 `test_equivalent_amounts_keep_separate_records` 佐证）。当前实现没有更新或删除记录的入口，`status` 永远是 `pending`；审批、支付等业务尚不存在。

## 6. SQLite 持久化与跨进程读取

已使用 SQLite 持久化。每次命令执行时 `_connect()` 新建连接（`cli.py:100-102`），submit 在 `with conn:` 块内先 `CREATE TABLE IF NOT EXISTS` 再 `INSERT`，块退出时自动提交、异常时自动回滚（`cli.py:110-116`），`finally` 关闭连接（`cli.py:118-119`）。list 同样先确保表存在再 `SELECT`（`cli.py:125-130`）。

因为数据落在 `--db` 指定的 SQLite 文件中、且每条命令都是独立进程独立连接，新进程对同一数据库文件执行 list 即可读到此前任何进程提交的记录——这正是 `test_expense_regression.py` 的测试方式（提交进程退出后由新进程查询，见该文件 docstring 与 `test_amounts_roundtrip_across_processes`）。进程重启后数据保留。

## 7. 查询如何筛选同一提交人的记录

`_query_expenses()`（`cli.py:122-142`）执行：

```sql
SELECT id, submitter, purpose, amount_minor, status
FROM expenses WHERE submitter = ? ORDER BY id ASC
```

- 匹配条件：清理（去首尾空白）后的提交人**完整名称精确相等**（`cli.py:166` 先清理，`WHERE submitter = ?` 等值比较）。前缀、子串、大小写或内部空格差异均不命中（回归测试 `test_prefix_substring_and_unknown_names_return_empty`、`test_inner_space_and_case_must_match_exactly` 佐证）。
- 排序：按 `id` 升序，即提交顺序。
- 返回：标准输出一行 JSON 数组，元素字段与 submit 返回的记录相同（`id`、`submitter`、`purpose`、`amount_minor`、`status`），`amount_minor` 为整数分。查无记录时返回空数组 `[]`，退出码 0（`test_fresh_database_returns_empty_list` 佐证）。

## 8. 失败情形的确定结果

以下结果均来自 `main()` 的异常处理（`cli.py:170-175`）：`ValidationError` → 标准错误输出 `参数错误: ...`、退出码 2；`sqlite3.Error`/`OSError` → 标准错误输出 `数据库操作失败: ...`、退出码 1。argparse 缺参数时自行打印 usage 到标准错误、退出码 2。所有失败情形标准输出均为空。

| 情形 | 触发位置 | 结果 |
|---|---|---|
| 空用途（去空白后为空） | `_clean_name`，`cli.py:153` | `ValidationError`，退出码 2 |
| 空提交人（去空白后为空） | `_clean_name`，`cli.py:152` / `cli.py:166` | `ValidationError`，退出码 2（submit 与 list 相同） |
| 零金额（如 `0`、`0.00`） | `parse_amount`，`cli.py:60-61` | `ValidationError("金额必须大于零")`，退出码 2 |
| 负金额（如 `-1`） | 正则不匹配，`cli.py:52-56` | `ValidationError("金额格式无效...")`，退出码 2 |
| 超过两位小数（如 `12.300`） | 正则不匹配，`cli.py:52-56` | `ValidationError("金额格式无效...")`，退出码 2 |
| 查无记录 | `_query_expenses` 返回空列表 | 正常结果：输出 `[]`，退出码 0 |
| 缺少必需参数（如 list 不带 `--submitter`） | argparse | usage 写入标准错误，退出码 2 |
| 数据库无法创建/打开/读写 | `cli.py:173-175` | 退出码 1 |

注意负金额与超两位小数走同一条"格式无效"路径，不单独区分；空金额字符串则是另一条"不能为空"消息（`cli.py:50-51`）。同一条件在当前实现下只有上表一个确定结果。

## 9. 固定示例

以下示例只使用 README 已公开的命令，在空目录下依次执行（演示金额 12.30 与 0.01，两位虚构提交人）。输出为对当前实现的实测结果；id 从 1 起是因为使用了全新数据库文件。

```sh
python -m expense_desk --db demo.sqlite submit --submitter 演示甲 --purpose 演示交通 --amount 12.30
# 退出码 0，标准输出：
# {"id": 1, "submitter": "演示甲", "purpose": "演示交通", "amount_minor": 1230, "status": "pending"}

python -m expense_desk --db demo.sqlite submit --submitter 演示乙 --purpose 演示办公 --amount 5
# 退出码 0，标准输出：
# {"id": 2, "submitter": "演示乙", "purpose": "演示办公", "amount_minor": 500, "status": "pending"}

python -m expense_desk --db demo.sqlite submit --submitter 演示甲 --purpose 演示餐费 --amount 0.01
# 退出码 0，标准输出：
# {"id": 3, "submitter": "演示甲", "purpose": "演示餐费", "amount_minor": 1, "status": "pending"}
```

按演示甲查询（新进程、同一数据库文件）：

```sh
python -m expense_desk --db demo.sqlite list --submitter 演示甲
# 退出码 0，标准输出（一行 JSON，按 id 升序，只含演示甲的两笔）：
# [{"id": 1, "submitter": "演示甲", "purpose": "演示交通", "amount_minor": 1230, "status": "pending"}, {"id": 3, "submitter": "演示甲", "purpose": "演示餐费", "amount_minor": 1, "status": "pending"}]
```

查询演示乙只返回 id 2 一笔；查询从未提交过的名字返回 `[]`（退出码 0）。金额在返回中均为整数分（1230、500、1），状态均为 `pending`。

## 10. 失败提交与重启保留的结论依据

**失败提交不留记录。** 依据有两层：其一，全部校验在打开数据库之前完成（`cli.py:151-157`），校验失败时根本不会执行 `INSERT`；其二，写入包在 `with conn:` 事务块中（`cli.py:110`），块内异常会回滚。回归测试 `test_invalid_submissions_do_not_change_existing_records` 逐项提交无效输入后复查，已有记录数量与内容均不变。

**结果在进程重启后保留。** 数据写入 `--db` 指定的 SQLite 文件并在 `with conn:` 退出时提交（`cli.py:110-116`）；读取方通过新连接打开同一文件（`cli.py:100-102`、`cli.py:123`）。回归测试的全部查询都在提交进程退出后的新进程中执行（`test_expense_regression.py:44-51` 的子进程调用方式），证明跨进程、跨重启可读。

## 11. 当前边界

- 没有审批、驳回、支付或状态变更入口；`status` 恒为 `pending`。
- 没有修改、删除、按用途/金额/状态筛选或分页的查询入口；唯一查询条件是提交人精确匹配。
- 没有 HTTP 或库级公开 API 的承诺；唯一公开入口是 README 描述的命令行。
- 记录不含时间戳，排序只保证按 id 升序（即提交顺序）。
